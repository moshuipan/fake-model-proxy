# 客户端协议对齐

FMP 的协议对齐目标是在明确的参考客户端及版本下，保持授权语义、设备上下文、
请求编码和响应处理一致。业务字段一致、假上游通过和官方渠道接受是三个独立的验证层次。
具体平台批准的授权或客户端证明不能由普通设备字段替代。

## 参考对象与证据

每个插件需要指明参考的是官方公开 API、Web 客户端、桌面客户端还是 CLI。
同一厂商的这些入口可能使用不同 OAuth 客户端、版本码、模型标识和请求格式，
不能把某个入口的参数移到另一个入口。

协议证据按以下顺序记录：

1. 官方 API 文档、官方发布包中的调用代码和公开 SDK。
2. 经过用户授权、已脱敏的实际请求与响应。
3. FMP 实现、隔离协议测试和历史记录。

第三类证据能证明 FMP 的行为和本地回归，不能独立证明服务器会接受该调用。
缺少原始客户端或真实请求时，保留明确的未知项，不把社区复现当作官方契约。
下载版本、公开来源、文件哈希和关键函数需要一起记录，以便客户端升级后复核。

## 版本与设备

GUI 应用版本、IDE 内核版本、CLI/SDK 版本、API 协议版本码和构建号需要分开建模。
即便某个协议版本码看似日期，也必须按客户端字段来源更新。
公开 API 插件按 API 契约发送所需字段，不接收其他厂商的设备头。

TRAE 个人版的 `client_device.app_version` 来自 `product.appVersion`；
`client_device.ide_version` 来自 `product.version`；
`plugin_version` 来自 `product.tronBuildVersion`。
原生 AI 扩展的 `X-Ide-Version-Code` 来自其 CN 区域配置。
原生设备头使用 URI component 编码，而个人商业活动 API 使用原始设备参数。
详见 [TRAE 个人版](../providers/trae.md)。

设备身份与会话身份分别管理。设备上下文按参考客户端的生命周期稳定保存，
不随账号选择或每次请求随机生成。物理设备配置属于服务；如果上游授权把设备标识
绑定到凭证，则保留并校验该关联，不能在请求阶段任意替换。
请求标识、授权 nonce 和协议要求的新会话标识按各自生命周期生成，
不能为了字节相同而复用一次性 nonce、旧刷新票据或已完成的请求。

## 实现边界

插件持有其请求上下文、端点、字段映射和响应解码规则。
公共 Gateway 只处理规范化请求、账号选择、预算、取消和统一错误语义，
不按厂商名称加入请求头或变更消息体。

已知的客户端元数据使用插件类型化配置与 schema。
未知版本或设备字段保持未知，不使用样例型号、随机数字或其他版本命名空间填充。
秘密继续使用独立存储与引用；设备报告、常规配置和协议测试不包含登录凭证。
连接身份发生变化时，通过 ConfigService 的版本化计划重建服务实例。

## 验证与维护

协议测试应断言必要字段的名称、值来源和编码，并覆盖授权恢复、流结束、
工具历史以及不应自动重试的拒绝响应。
固定测试向量用于编码和格式验证，必须标为隔离测试，不能作为真实网络结果引用。
不能把全部实现字段简单复制到预期值，形成只检验实现本身的测试。

修正某个接口后，核对该插件的其他接口是否使用了不同的头、版本或请求来源参数。
完成规定构建与测试后，重新导出管理契约；实际运行版本仍以在线插件目录为准。
官方渠道拒绝、设备证明缺失和未知执行保留为独立限制，不通过重放、伪造证明
或轮换身份去掩盖失败。
