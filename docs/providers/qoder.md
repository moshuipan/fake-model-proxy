# Qoder 试聊与排队提示

## 客户端协议对照与完成用量

2026-11-24 对照官方 CLI `1.1.96`。该来源不能证明既有 IDE/COSY `1.0.10`
的所有 wire 字段应改为 CLI 字段；body/API/CLI 版本分别保留。
新 CLI 的 WASM 最终签名、设备身份、推理地址与活动 claim 契约尚未确认。

流读取在 `finish_reason` 后保留同帧和尾随 usage，等待 DONE、EOF 或最多一秒尾帧期限，
最后只发送一次终态。取消仍覆盖读取和发送；坏内层 JSON 显式报错。
识别 `event: finish`、额度标记和 notification 元数据，混合 LF/CRLF 按最早帧尾读取。
这修正了完成同帧 usage 被提前 return 丢弃的源码错误，不代表已验证官方线上生成。

在控制台选择「Qoder / auto」调用的是 Qoder 的 `auto` 模型。未指定后端的 `auto` 则是代理的自动路由，两者含义不同。

## 图片与工具结果

当前 Qoder 私有封包只在 user 消息的 `contents` 中编码图片，其他角色使用
文本 `content`。2026-11-22 假上游复现确认：一张 tool 结果图片曾被丢弃，
下游仍收到 HTTP 200。修复后适配器声明这一表达限制，
Auto 在准入时排除这类请求的 Qoder 候选；显式 Qoder 调用返回 HTTP 400
与 `image_role_unsupported`，且不提交上游。开启目录或配置的图片能力不能绕过限制。
user 图片仍保留原有封包；该回归只验证传输，不能证明真实模型接受或识别图片。
截图工具结果需要选择能够表达工具图片的后端。

## 工具历史错误 2013

`invalid params, tool call result does not follow tool call (2013)` 是上游
HTTP 400 的工具历史关联拒绝。`qoder_envelope_error` 是适配器对普通信封错误的
分类，真正的诊断依据是内层消息；不是额度或排队信号。

2026-11-23 严格假上游复现了两条源码路径：Responses 将同一轮 A/B 调用拆成
两条 assistant 消息，再发送 A/B 结果；Messages 在同条混合内容的多个结果之间
插入普通 user 正文。两者均能通过真实 Qoder 封包路径复现相同的 400/2013。
修复后 Responses 合并同轮调用，Messages 连续发送结果再发送普通正文。
三协议统一拒收不完整或不匹配的工具历史，返回本地 `invalid_tool_history`，
不向 Qoder 提交。这是源码及假上游证据，真实故障请求仍需结合部署日志核对。

## 签到与活动领取

2026-11-19 已修正活动字段解析：`GET /sash/api/v1/me/campaigns` 返回
`campaignId`、`actionType` 和 `claimStatus`。只处理 `CLAIM_BENEFIT`，
`CLAIMABLE` 才提交领取；`CLAIMED` 显示「当前积分活动已领取」，详情链接不会领取。
此前代码只识别 `status` / `id`，真实的已领取状态被误显示为「无可领取活动」。

领取使用 `POST /sash/api/v1/me/campaigns/{campaignId}/claim` 和空请求体。
成功要求明确 `status=CLAIMED` 和 `grantId`；`replayed=true` 表示幂等重放。
奖励只读取领取响应的 `benefit.amount`（`kind=CREDITS`），不把列表中的预告奖励当作实发积分。
响应不确定时记录「未知」，不自动重放。

每个任务只处理记录对应的账号。手动签到和调度器共享互斥，避免并发领取。
Qoder 活动窗口可能跨自然日，所以每次触发都先查询上游；
代理同日的已完成记录不会挡住新活动窗口。空活动列表只表示上游未下发可领取活动，
不能据此推断账号没有积分或登录失效。

## 模型名称与调用 ID

模型目录同时返回内部 `key` 与用户可读的 `display_name`。例如，本次真实目录的 `qmodel_latest` 显示为 `Qwen4-Max`，`gmodel` 显示为 `GLM-5.3`。内部 ID 是路由协议的一部分，不应改成展示名称。

同步后，代理将完整模型目录和独立调用名称保存到 SQLite。列表、下拉、服务详情及请求记录显示官方名称；外部客户端和复制操作使用调用名称，例如 `qoder-qwen4-max`。模型白名单及上游请求仍使用原始 key。Qoder 固定模式名按中文显示：Auto → 自动，Ultimate → 极致，Performance → 快速，Efficient → 经济；未返回的模式不会自行补进目录。搜索支持显示名、调用名称和原始 ID。页面刷新及服务重启从本地缓存读取，不因浏览页面重复访问上游。

已有服务需重新同步一次补齐名称。目录是可重新读取的缓存，配置导入后可再次同步。模型名称以上游当前目录为准，不对未返回的模型自行建立别名。

## 积分消耗倍率

目录中的 `price_factor` 表示上游下发的相对积分消耗倍率，例如 `0.2` 显示为 `0.2×`。同步会将倍率与模型名称一并保存到 SQLite，模型列表、下拉、服务详情和 `GET /v1/models` 均能读取。重新同步会更新倍率，现有模型 ID 不变。

上游同时提供 `original_price_factor` 时，页面展示划线的优惠前倍率和当前倍率。例如本次国内目录的 Qwen4-Max-Preview 为原倍率 `0.5×`、当前倍率 `0.1×`。没有原倍率时不推测折扣。

倍率缺失或无效时显示「倍率未知」，不会推算成零；只有上游明确返回零才显示 `0×`。这是积分倍率，不是每 Token 的货币单价。目录中的上下文档位只提供 token 数，未提供单独倍率，因此本版不编造按上下文档位计算的价格。不同厂商的倍率基准不能直接横向比较，实际扣除积分及活动折扣以上游为准。

## 排队行为

Qoder 可能在 HTTP 200 的 SSE 响应内返回 `statusCodeValue=403`，错误正文嵌套三层 JSON。业务码 `10605` 和明确的 `isQueued=true` / `retryAfterSeconds>0` 表示模型容量紧张，不等于账号登录失效。

代理收到该信号后及时返回 `qoder_queued`：

- 非流式 Chat、Messages 和 Responses 返回 HTTP 429 与可读提示。
- 启动缓冲内发现排队的流式请求也返回 HTTP 429；已输出内容的流发送协议错误事件并结束。
- 提示中的等待时间取上游 `retryAfterSeconds`，缺失时参考 `waitTime`。
- 代理可在统一预算内尝试其他可用账号；没有目标时及时返回，恢复时间通过
  `Retry-After` 提示，不隐藏等待 60 秒。冷却期内同模型请求在本地拒收。
- FMP Auto 遇到排队后，本次请求跳过该账号的其他模型，避免在同一账号上连续提交
  `gmodel`、`mnmodel`、`auto` 等生成。仍可尝试其他账号或服务的合格模型。
  这个避让只属于本次请求，后续请求的冷却范围仍是后端模型，不扩大成账号禁用。
- 每请求或共享服务重试预算用尽时，已有的 `qoder_queued` HTTP 429 和恢复提示
  保持不变；不会用尝试次数耗尽的 HTTP 503 覆盖排队原因。
  全部合格模型仍因限流冷却时，后续请求返回 `gateway_target_cooling` HTTP 429
  与最早恢复时间，不向上游提交。
- 模型排队不会触发整个账号的鉴权冷却，也不会静默切换当前精确选择的模型。

`isQueued=false` 且没有建议重试时间的 `RESOURCE_LIMIT` 保留为资源或套餐权限错误（HTTP 403），不能仅因错误正文出现 `isQueued` 字段名就当作排队。

并发容量默认每账号 4、每服务 16，这是 FMP 的准入设置，不是 Qoder 的并发保证。
排队可能来自模型资源紧张，也可能与账号同时生成数量有关，不能仅凭 429 判断限额。
确认账号只允许一个生成后，可通过配置服务将
`gateway.targets["服务ID/账号ID"].capacity` 设为 1；租约覆盖完整响应流。
超出的请求在 FMP 内等待，默认最多 10 秒、队列容量 128，等待到期仍会返回
`gateway_capacity_timeout` HTTP 503。降低容量不能消除模型级排队。

## 普通 HTTP 429 与并发定位

普通 HTTP 429 与 `qoder_queued` 都直接交给统一网关，不在 Qoder 适配器中
用同一账号轮流提交到国际站的三个端点。普通 429 按账号冷却，模型队列仍按
后端模型冷却；原始 `Retry-After` 保留，其他合格账号可在总预算内接替。
确认未执行的非限流错误仍可换端点，服务端未知执行不会重放。

每次尝试的 Trace `routing.admission` 保存原子准入完成时的
`service_in_flight` / `account_in_flight`、对应 `capacity`、`service_qps`
及该服务滚动窗口中的提交和预占数 `service_submissions_in_window`。
这些是准入时刻的数据，后续释放容量不会改写；不包含凭证或消息。
控制台「请求详情 → 上游尝试」展示同一快照，可查看该次限流对应的账号及负载。
达到每秒 10,000 条的历史保留上限后，窗口数只是保留数量。
QPS 限制控制请求开始频率，capacity 控制完整响应流同时占用的数量，两者不能互相替代。

TRAE 4054 属于客户端错误，不能单凭这个码确定是上游限流或流协议错误。
定位时关联故障时间、响应的 `x-request-id` 和 FMP Trace，先判断是启动前
HTTP 429、输出后的流错误，还是成功终态被客户端拒绝，再检查对应客户端日志。

## 已定位的问题

2026-11-19 的真实复现中，上游约 0.6 秒返回排队，建议等待 60 秒，账号有 296/300 credits 且 `serviceAvailable=true`。旧实现内部等待两次，控制台在 121.4 秒后才显示转义 JSON。修复后应及时显示排队原因。

当时 `efficient` 对照也返回排队（建议 30 秒）。该证据只表明模型资源紧张，不能承诺切换模型后就能生成内容。代理能修复等待和错误展示，不能消除上游队列。

2026-11-22 的本地假上游复现确认：普通 HTTP 429 曾触发同账号向三个端点连续
发出 3 次 POST，消耗 3 次生成预算。修复后为 1 次，保留恢复提示并由网关调度。
这证明适配器存在限流放大问题，尚不能据此确定另一台机器上的 4054 根因。

## 回归验证

`tests/qoder_flow.rs` 用假上游验证三协议及时报告队列、并发排队及冷却后的 429 /
`Retry-After`、流内错误不重放、队列不禁用账号、资源不可用与排队区分，以及数字业务码识别。
`tests/gateway_flow.rs` 验证共享重试信用耗尽后的并发限流、同请求的账号避让和跨账号恢复。
Qoder 适配器的本地 HTTP 测试验证普通 429 不换端点、安全恢复与未知执行边界；
`tests/qoder_flow.rs` 验证普通 429 的跨协议恢复提示、账号级冷却及跨账号恢复。
`tests/protocols.rs` 同时启动四个 TRAE Responses 会话，检查正文、工具参数、
响应身份和完整 SSE 生命周期隔离；该测试不能代替真实 TRAE 客户端验证。
`tests/multimodal_routing.rs` 验证三协议工具图片的显式拒收、
Auto 避开无法编码的 Qoder 候选，以及 user 图片的原生封包保留。
`tests/tool_history.rs` 的严格假上游验证真实 Qoder 及标准兼容封包的连续工具批次、
逆序结果、多轮历史、混合正文、本地拒收及并发会话隔离。
所有测试不使用真实凭证。
